# 0003: CAS-fenced task lifecycle and a durable worker loop

## Status

Accepted. `session_handle` and `session_human_review` now enqueue through `TaskService.enqueue` and return; `_startup_maintenance` starts `_MAX_CONCURRENT_PIPELINES` `Worker` instances that claim and execute the real `pipeline_run`/`pipeline_resume` handlers. See Consequences for what is still open.

## Context

`session_handle` and `session_human_review` (`server.py`) each launched pipeline work as a bare, per-request `asyncio.create_task(worker())` closure with no persisted lease, no fence, and no independent recovery path: a process restart mid-run silently orphaned the task (recovered only by a 900-second wall-clock "orphaned by process restart" sweep, `server.py`'s `_startup_maintenance`), and two requests racing the same session had no CAS boundary preventing a double-accepted effect.

## Decision

`backend/phi_core/control/tasks.py::TaskService` owns every `work_items` state and lease transition: `enqueue`, `claim`, `heartbeat`, `complete`, `fail`, `cancel_subtree`, `reconcile_leases`. Every transition made by an already-claimed holder (`heartbeat`, `complete`, `fail`) is one `ControlStore.compare_and_set` call filtered on `lease_owner` and `fence`; `claim`'s filter is `state == "ready"` (the state flip is itself the uniqueness guard against two racing claimants); `complete`/`fail` bump `fence`. A caller whose `lease_owner`/`fence` no longer matches the stored document gets back `TaskOutcome(outcome="fenced")`, never an exception and never a silent no-op that looks like success. `cancel_subtree` walks every `parent_task_id` descendant of a task within a run and best-effort CAS-flips each non-terminal one to `cancelled`, bumping its fence so an in-flight stale holder's next `complete`/`fail` is rejected. `reconcile_leases` returns an expired `leased` task to `ready` (or fails it past `max_attempts`, bumping fence either way).

`control/worker.py::Worker` is the claim-and-lease loop: it polls `TaskService.claim` for `ready` work items whose `task_type` has a registered handler, heartbeats while the handler runs, and reports through `complete`/`fail`, discarding a `fenced` outcome silently (a fenced result means a different worker now owns the task). `drain_outbox` reads embedded `OutboxEntry` records and dispatches by `kind` to a handler registry, leaving an entry with no registered handler `pending` rather than dropping or erroring it. A reconciler wraps `TaskService.reconcile_leases` on a fixed `LEASE_RECONCILE_INTERVAL_S`.

`_startup_maintenance` starts `_MAX_CONCURRENT_PIPELINES` `Worker` instances (not one), each with the real `{"pipeline_run": _handle_pipeline_run, "pipeline_resume": _handle_pipeline_resume}` registry -- a single worker claims and executes strictly one task at a time, so matching the concurrency `_admit_pipeline_run`'s in-process counter already promises (and the immediate 429 it returns past that cap) needs exactly that many workers polling the same `work_items` collection; `TaskService.claim`'s CAS makes two workers racing the same task safe regardless of worker count. `session_handle`/`session_human_review` keep the admission check (`_admit_pipeline_run`, immediate 429) in the route, before enqueue, preserving the exact current throughput and overload-response contract; `_handle_pipeline_run`/`_handle_pipeline_resume` release the slot (`_release_pipeline_run`) when the pipeline genuinely finishes, in their own `finally` block, not when the route returns. `control/policy.py::MANIFESTS` gained a `"Pipeline"` entry (`task_types={"pipeline_run", "pipeline_resume"}`) since the top-level enqueued unit makes no provider call and activates no grant of its own -- every real agent activation inside `run_agent_pipeline`/`execute_decisions` still opens its own separate `make_ctx`-issued grant.

## Consequences

- A process crash mid-run now recovers automatically and faster than before: once a claimed task's lease expires (`LEASE_SECONDS=60`, extended by a heartbeat every `HEARTBEAT_INTERVAL_S=20` while a handler runs), `reconcile_leases` returns it to `ready` and the next `Worker` poll (`DEFAULT_POLL_INTERVAL_S=1`) picks it back up, re-running the handler from the top. This replaces the previous 900-second "orphaned by process restart" sweep's only recovery path (mark the session `failed`, require a manual resubmission) with an automatic retry, up to the grant's `max_attempts` (3).
- The 900-second orphan sweep in `_startup_maintenance` is intentionally unchanged, not removed: it is now the backstop the plan's step 8 asks for, catching a session whose `WorkItem` exhausted every retry attempt and reached a terminal `failed` state with no corresponding write back to the session document (`reconcile_leases`/`TaskService` know nothing about session documents; only the sweep currently closes that loop), plus any pre-migration session with no `WorkflowRun` at all.
- `control/worker.py`'s `OUTBOX_HANDLERS` registry is still empty: nothing in this migration produces an `OutboxEntry`, so `drain_outbox` still has nothing to relay. Step 10's boundary kill tests, which need a real handler to kill the process between its CAS and the relay's execution of that entry, remain out of scope until a caller populates the outbox.
- Full `TaskService`-lifecycle management of Scout as a durable child `WorkItem` (Phase 4 step 5's "Scout becomes a durable child task") is still open: it requires `AgentContext` to carry the claimed lease `fence`, which it does not yet. Scout's `asyncio`-level leak (a background task left running past its caller's return) is already closed, independent of this gap -- see `docs/adr/0001-workflow-engine.md`.
