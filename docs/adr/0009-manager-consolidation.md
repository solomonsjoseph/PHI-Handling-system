# 0009: Manager and ManagerSupervision as two independent classes in one module

## Status

Active. Supersedes the "two separate, both-live supervision authorities" state ADR 0006's own Status section describes (`Manager` as a broker owning `ROLES`/`BUDGET_S` bookkeeping plus Judge-specialist handoffs, and `SuperOrchestrator` owning `workflow_runs` lifecycle state).

## Context

Rewrite plan step 7 ("SuperOrchestrator becomes Manager, one entity with one name that sequences the run") asked for a single renamed class holding D9's sequencing authority. Two pre-existing classes carried the word "Manager" already, at two different meanings, in two different packages:

- `phi_core/control/superorchestrator.py::SuperOrchestrator` -- the D9 sequencing authority (`start_run`, `advance`, `create_child_work`, `request_human_review`, `recover`, `authorize_manifest_freeze`, `rewind`, `close_run`, ...). Not an `Agent` subclass. Constructed `SuperOrchestrator(store, tasks)` at every call site (server.py's 11 lifecycle routes, several `agents/orchestrator.py` command sites).
- `phi_core/agents/manager.py::ExecutionHealthSupervisor` -- the agent-facing execution-health supervisor (`run`, `note_phase`, `run_supervised`, `consult`, `respond_to_handoff`, `respond_to_handoff_budget`, `close_run`) plus the deterministic guardian query broker (`attach_schema`/`ask_schema`, `attach_instrument`/`ask_instrument`, `attach_lexicon`/`ask_lexicon`). An `Agent` subclass, `NAME = "Manager"` (the persisted agent-identifier string every `AgentContext`/`AgentManifest`/capability grant/task record keys on). Carried a backward-compatibility alias, `Manager = ExecutionHealthSupervisor`, at the bottom of the module for the one caller (`server.py`'s human-review-resume path) that had not yet migrated off the pre-rename name. `AgentContext.manager` (the field every agent reaches via `ctx.manager`/the `Agent.manager` property) always held an `ExecutionHealthSupervisor` instance -- never a `SuperOrchestrator` instance.

Both classes are constructed independently, at different call sites, with different lifecycles: `ExecutionHealthSupervisor` is constructed once per pipeline run and lives in `_PipelineDriverState.manager` for the run's duration; `SuperOrchestrator` is constructed fresh, disposably, at each D9 command call site (inside `_escalate_to_human_review`, inside the manifest-freeze helper, inside the rewind-routing helper, inside `run_pipeline`'s own dispatch loop, inside every server.py lifecycle route). Neither one ever wraps, constructs, or holds a reference to the other anywhere in the pre-existing, unchanged production code.

An earlier drafting pass of this ADR's implementation attempted to make the renamed `Manager` wrap a `ManagerSupervision` instance behind a six-method delegating facade (`run_supervised`/`consult`/`note_phase`/`close_run`/`respond_to_handoff`/`respond_to_handoff_budget`), reasoning from the rewrite plan's own step title ("Restructure the Manager as facade plus supervision"). This produced two real defects before either class was renamed anywhere else: `Manager.run()` silently shadowed `ManagerSupervision`'s -- meaning `ManagerSupervision.run()` initially had no implementation at all, `and would have raised AttributeError from state.manager.run(...)` in `agents/orchestrator.py`'s `_prepare_pipeline_state`, an existing, unchanged production call site -- and the entire guardian query broker (`attach_schema`/`ask_schema`/etc.) was placed on the wrong class for the same reason (`state.manager.attach_lexicon(...)` in `agents/orchestrator.py::run_pipeline` is unambiguously called on the `ManagerSupervision`-typed `state.manager` field, never on a `Manager` instance). A full grep of every real call site confirmed `Manager(store, tasks, ctx=...)` -- the three-argument construction the facade design would have required -- has zero callers anywhere in the codebase; every construction site passes exactly two positional arguments. The facade design was reverted before landing.

## Decision

`phi_core/control/manager.py` holds two fully independent classes. Neither wraps, delegates to, or references the other's instance state:

- `Manager` -- renamed from `SuperOrchestrator`, byte-for-byte behavior preserved except the ten already-zero-production-caller methods this phase deletes (`resume`, `dependencies_satisfied`, `observe_handoff`, `require_artifacts_current`, `evaluate_handoff_budget`, `route_budget_exceeded`, `authorize_execution`, `begin_export`, `confirm_export`, `authorize_publication`; see `docs/FUTURE_WORK_DEFERRED_AGENTS.md`-adjacent disposition notes for why each has no caller). `__init__(self, store: ControlStore, tasks: TaskService) -> None` -- exactly `SuperOrchestrator`'s original two-argument constructor. No inheritance from `Agent`. No `NAME`, no `ROLES`, no `BUDGET_S` -- it never supervises an agent's execution health, only sequences the workflow.
- `ManagerSupervision` -- renamed from `ExecutionHealthSupervisor`, byte-for-byte behavior preserved, including the guardian query broker (`attach_schema`/`attach_instrument`/`attach_lexicon`/`_record_handoff`/`ask_schema`/`ask_instrument`/`ask_lexicon`) and `run()`. `__init__(self, ctx, *, db=None) -> None` -- exactly `ExecutionHealthSupervisor`'s original constructor. Subclasses `Agent`. `NAME = "Manager"` is unchanged: the persisted agent-identifier string stays `"Manager"` regardless of the Python class name, since every `AgentContext`/`AgentManifest`/capability-grant/task record already keys on that string, and changing it is a separate, unrelated, much larger cross-cutting change this phase does not make. `AgentContext.manager`'s type annotation becomes `ManagerSupervision | None` (previously an `agents.manager.Manager`-aliased forward reference); its runtime value is unchanged -- the same object, under its new class name.

The backward-compatibility alias (`Manager = ExecutionHealthSupervisor`, and its downstream consumers: `phi_core/agents/__init__.py`'s `from .manager import Manager` re-export, `phi_core/agents/base.py`'s `TYPE_CHECKING`-only reference, and three test files that imported the alias directly) is deleted outright, not kept. `agents/manager.py` and `control/superorchestrator.py` are both deleted; their full content lives in `control/manager.py` under the new names.

Both classes happening to define a method named `close_run` is not a collision: `Manager.close_run(self, *, run_id: str) -> dict` (the D9 read/verify closure-eligibility check) and `ManagerSupervision.close_run(self, outcome: str) -> dict` (the run-report method every pipeline run calls once per settled exit) are on two unrelated classes that never coexist on one object, exactly as `SuperOrchestrator.close_run` and `ExecutionHealthSupervisor.close_run` never did before this rename either.

Moving `ManagerSupervision` from `phi_core/agents/` into `phi_core/control/` closes a real circular import that a naive move opens: `ManagerSupervision(Agent)` needs `agents.base.Agent` at class-definition time, and `agents/base.py`'s own package, `phi_core/agents/__init__.py`, previously eagerly imported `agents/orchestrator.py` (`from .orchestrator import run_pipeline`) -- which itself needs `control.manager.Manager`/`ManagerSupervision` at module level. `phi_core/agents/__init__.py` no longer imports `.orchestrator` eagerly; `server.py`'s one caller of the package-level `run_pipeline` re-export now imports it directly from `phi_core.agents.orchestrator`.

## Consequences

- Every `SuperOrchestrator(...)` construction site (server.py's 11 routes, `agents/orchestrator.py`'s several D9 command helpers, `control/activation.py`, `control/context.py::StoreOpaqueWriter`, `control/cleanup_manager.py`, `control/manifest.py`, `control/rewind.py`, `control/testing.py`) becomes `Manager(...)`, unchanged arity.
- Every `ExecutionHealthSupervisor(ctx, db=...)` construction site (server.py's post-run-report path, `agents/orchestrator.py::_prepare_pipeline_state`) becomes `ManagerSupervision(ctx, db=...)`, unchanged arity and unchanged runtime object identity at `state.manager`/`ctx.manager`.
- `phi_core/agents/__init__.py` no longer re-exports `run_pipeline` or `Manager`; callers import `phi_core.agents.orchestrator.run_pipeline` directly.
- `test_manager.py`, `test_manager_broker.py`, `test_resilience_timeouts.py` (previously testing `ExecutionHealthSupervisor` under its `phi_core.agents.manager.Manager` alias) now import `from phi_core.control.manager import ManagerSupervision as Manager` -- a local aliasing import, not a re-introduction of the deleted module-level alias. `test_manager_broker.py`'s `test_manager_is_the_execution_health_supervisor_compat_name` (asserting `Manager is ExecutionHealthSupervisor`) is deleted outright: there is no longer an alias relationship to assert, only one class under one name.
- `test_architecture_boundaries.py::test_manager_holds_no_workflow_authority`'s static check ("this class never imports `control.tasks`/`control.artifacts`/`control.review`") can no longer read the whole source file's import statements, since `control/manager.py` now also contains `Manager`, which legitimately imports `control.tasks`. It instead asserts, at runtime, that `ManagerSupervision.__init__`'s parameters exclude `store`/`tasks` -- a structural guarantee (the class cannot even receive a `ControlStore`/`TaskService` reference) rather than a textual one.
- `docs/adr/0006-super-orchestrator.md` is a historical record of the pre-Task-7 state and is not rewritten; this ADR is the current authority for the `Manager`/`ManagerSupervision` split. `docs/adr/0007-agent-teams.md`'s "`Manager` remains supervisory" sentence needs no correction: it describes the concept, which is unchanged.
