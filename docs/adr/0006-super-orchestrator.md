# 0006: Super Orchestrator as the exclusive workflow-state authority

## Status

Superseded. `control/superorchestrator.py::SuperOrchestrator` still exists and is tested, but the core claim here (that it is the exclusive workflow-state authority) no longer holds. As of Phase 17-C the system has two separate, both-live supervision authorities: `Manager` (a broker owning `ROLES`/`BUDGET_S` bookkeeping and Judge-specialist handoffs) and `SuperOrchestrator` (owning `workflow_runs` lifecycle state). A large fraction of `SuperOrchestrator`'s published API (`resume`, `dependencies_satisfied`, `observe_handoff`, `require_artifacts_current`, `evaluate_handoff_budget`, `route_budget_exceeded`, `authorize_execution`, `begin_export`, `confirm_export`, `authorize_publication`) is built and tested but dormant, with zero production callers. See `docs/PHASE_STATUS.md` (Phase 17-C).

## Context

`control/workflow.py`'s D9 node table and `TRANSITIONS` map (Phase 4) were fully built and tested, but nothing in production ever called `next_node`: `workflow_runs.node` was stamped `"charter"` at creation and never advanced. `session_handle` atomically claims its session, then calls `SuperOrchestrator.start_run` with that claim's fresh `run_id`; the orchestrator creates the matching `WorkflowRun` and durable `pipeline_run` root task. `session_human_review` still directly enqueues `pipeline_resume`; `Manager.escalate_to_human_review` still writes human-review state directly. Publication still has a lazy download-triggered path in `server.py::_open_published_artifact`.

Two pieces of Phase 5's plan text had already been landed by an earlier phase and needed no new code: `ArtifactService.certify_publication`/`PublicationPointer` (already production-called from `server.py:1197`, already tested in `test_control_artifacts.py`) and `control/policy.py::TEAMS` (already defined with the exact five requirement labels). This phase adds `docs/adr/0007-agent-teams.md` and `test_control_bounds.py`'s exact-partition assertion; D5's individual resource-ceiling tests remain open.

## Decision

`SuperOrchestrator(store, tasks)` exposes the ten D9 methods. It never writes `work_items` (that stays `TaskService`'s exclusive authority, including for a child's acceptance -- see `accept_result` below), never writes `workflow_runs.decision_version` (that stays `run_decision_gates`'s D11 authority), and calls into `ArtifactService` for publication without owning `artifacts`/`publication_pointers` itself.

D9's published method signatures list bare identifiers only, but three methods need a value this class cannot safely re-derive from persisted state alone:

- `advance(*, run_id, outcome)`: which outcome a node reached (did a gate pass? did a reviewer approve or defer?) is not recoverable from `workflow_runs` alone without a bespoke, unverifiable derivation rule per one of the fifteen non-terminal nodes. The caller -- the pipeline handler that just observed the real `GateOutcome`/`HumanReviewEvent.kind`/child-acceptance result -- reports it directly, exactly like `TaskService.complete`/`.fail` and `ArtifactService.certify_publication` already do at every other typed-result boundary in this codebase. `next_node` remains the sole authority translating that reported outcome into the next node: an unmodelled `(node, outcome)` pair fails closed (`WorkflowError`), so a caller can report what happened but can never invent an outcome that skips, reorders, or disables a gate.
- `request_human_review(..., task_id="", required_role="")`: `HumanReviewRequest.task_id` has no default in D3's record definition (`records.py:346`); these two keyword-only additions default to `""` so every existing call keeps D9's exact arity.
- `authorize_publication(*, run_id, artifact_ids=None, gate_result_ids=None, certified_by_task_id="")`: the winning artifact set is computed today from `db.sessions["guard_report"]`/`export_paths`, a plain Motor document field entirely outside `ControlStore`'s abstraction; `SuperOrchestrator` has no access path to it and must not invent one. A `None`/empty `artifact_ids` is a query-only mode returning the current generation (`0` if none was ever certified); a non-empty list delegates to `ArtifactService.certify_publication` with a fresh fence. Refuses (`WorkflowError`) while any `HumanReviewRequest` for the run is `open`.

`accept_result` is a pure decision function with no `work_items` side effect: `TaskService.complete`'s `succeeded` state is infrastructure-level completion, not acceptance ("a child's success is not acceptance, and a child cannot accept its own material result" -- step 5). It verifies the task belongs to the run, has actually reached `succeeded`, and that the caller-asserted `result` is byte-identical to the task's own fenced `output_ref` -- never a caller-asserted value that could diverge from what the claimed worker actually wrote -- then records the task id into `workflow_runs.checkpoint["accepted_task_ids"]` under a retry-CAS loop (the same optimistic-retry pattern `gates.py::_next_decision_version` already uses). Returns `False`, never raises, for every refusal reason; idempotent on an already-accepted task.

`create_child_work` derives the enqueuing `worker` (an agent name) from the caller-supplied `task_type` alone via a reverse lookup over `MANIFESTS` (`_worker_for_task_type`), since D9's signature has no `worker` parameter; validates depth/fanout through the already-existing `CapabilityPolicy.check_child` (exposed read-only via a new `TaskService.policy` property); and separately refuses a proposed `budget` that asks for more than the target agent's own manifest, bounded by the global D5 ceilings, already authorizes (`_budget_widens`), reusing `policy.py::_bounded_budget`.

## Consequences

- `session_handle` is the first production entry path through this class. Its session-document CAS remains the sole admission/idempotency boundary; it passes its freshly minted run id into `start_run`, so the claim, `WorkflowRun`, and root `pipeline_run` `WorkItem` share one identity. `start_run` is the sole `TaskService.enqueue` caller for that root task. The pre-existing session status/error response contract and route-level concurrency cap are unchanged.
- Step 2 is complete. `session_human_review` reuses its existing `run_id` and asks `start_run` for a `pipeline_resume` root; an existing `WorkflowRun` is reused instead of inserting a second `"charter"` record, while a pre-migration session receives its first durable record under its legacy token. `session_cancel` mirrors its legacy session flag into `cancel_run`; `session_delete` tombstones first, then lets `cancel_run` recursively fence root work and descendants before artifact erasure. `corpus_study_research` and `settings_warmup`/`_run_warmup` (shared with `_warmup_scheduler_loop`) each call `start_run` (`run_type="maintenance"`/`"warmup"`) before their `ActivationFactory`-issued grants -- the missing piece was never grant/budget enforcement (both already had that) but the durable `WorkflowRun` D5's run-level bounds need to check against. `session_intake`, `corpus_study_generate` remain direct: neither does provider or workflow work. `_startup_maintenance`'s orphan-run reconciliation still marks a stuck legacy `sessions` document `failed` directly rather than also transitioning its `WorkflowRun`; low-value boot-time recovery, tracked as residual risk rather than fixed here.
- Step 4 is complete: `Manager.escalate_to_human_review` is deleted. Its four `orchestrator.py` callers, plus `run_pipeline`'s decide-loop escalation, now call a shared `orchestrator._escalate_to_human_review` helper that persists the session document itself (Manager keeps `close_run` for the deterministic report, and its `_escalation` bookkeeping is set by the caller, not internally) and then calls `SuperOrchestrator.request_human_review` with the exact D9 node each escalation site models (`"human_review_decisions"` for the executor-crash and decide-loop paths, `"human_review_audit"` for the reviewer- and auditor-stage paths, per `workflow.py`'s own TRANSITIONS-grounding comment). Tolerates an unknown `run_id`/absent `store` -- the tested, load-bearing session-document write never depends on the durable request succeeding, since not every existing caller (tests, and any route that has not yet opened a run through `start_run`) has one yet.
- Step 5 is complete: Ledger's Compare/Aggregate and Herald's Abstract/Sections are `create_child_work` children of their parent's task, gated by a non-empty `allowed_child_task_types` on the `Ledger`/`Herald` manifests. `SuperOrchestrator.accept_result` is the sole authority accepting each child's material result; a child's `succeeded` state alone is infrastructure completion, not acceptance. Converting them surfaced a real, pre-existing gap this step also fixed: no synchronous-pipeline agent activation ever completed its own `WorkItem` (`ActivationFactory.activate` claims a task and hands back a context, but nothing transitioned it out of `leased`), so `create_child_work`'s live-task accounting -- the first real caller of `MAX_PARALLEL_TASKS_PER_RUN`/`MAX_TASKS_PER_RUN` against real accumulated state -- would have failed in any real run, not only a test. `Agent.__init_subclass__` now wraps every leaf subclass's `run()` to complete (or fail) its own task against a new `AgentContext.tasks` (`TaskCompleter` protocol, `StoreTaskCompleter` implementation, wired by `ActivationFactory`); Praxis's `method_for()`, the one calling convention that bypasses `run()`, completes explicitly at its two call sites (`orchestrator.py`'s per-category loop and `server.py`'s shared warmup context).
- Step 6 is complete: `TEAMS` has its exact-contract test and ADR 0007.
- Step 9 is complete: `control/adapters.py` and its dedicated test file are deleted; the adapter layer is gone.
- Step 7 is complete. All 17 D5 bounds relevant to enqueue/gateway-time enforcement are checked and tested (`test_control_bounds.py`): the 6 enqueue-time bounds `create_child_work` already covered, the 4 already-grant-scoped per-task ceilings (wall/tokens/cost/tool-calls) `ProviderGateway.complete` now checks explicitly rather than only via the grant's own budget, 2 new byte-size ceilings (`MAX_INPUT_BYTES`/`MAX_OUTPUT_BYTES`), and 5 run-level aggregates (`MAX_RUN_WALL_S`, `MAX_TOKENS_PER_RUN`, `MAX_COST_PER_RUN_USD`, `MAX_TOOL_CALLS_PER_RUN`, `MAX_ARTIFACT_BYTES_PER_RUN`) via a new accumulator in `control/runs.py` (`check_run_budget`/`record_run_usage`) that `WorkflowRun.usage`/`.budget` already had fields for but nothing populated or checked. `BudgetExceeded` (a `CapabilityDenied` subclass) distinguishes a genuine resource-ceiling refusal from an identity/scope/data-class denial; every refusal -- `create_child_work`'s and the gateway's alike -- is recorded as a `TraceEvent(outcome="budget_exceeded")`, satisfying the plan's per-bound requirement literally, using `StoreTraceWriter`'s existing `event_seq` CAS-allocation (gateway.py duplicates the ~15-line allocation loop rather than importing it, to avoid a `context.py`<->`gateway.py` import cycle). The remaining bounds (lease/heartbeat timers, and the Phase-7-scoped collection-size ceilings `MAX_RATE_BUCKET_KEYS`/`MAX_CHATGPT_LOGINS`/`MAX_SESSION_PROGRESS_EVENTS`/`MAX_OUTBOX_ENTRIES_PER_DOC`/`MAX_CHECKPOINT_PAYLOAD_REFS`) are out of this step's scope by the plan's own phase boundaries.
- Step 8 is complete, with one documented, intentional exception recorded precisely rather than hidden. `control/activation.py::ActivationFactory.activate` remains a real, currently-necessary `TaskService.enqueue` caller outside `superorchestrator.py`: every individual agent activation across the entire pipeline (Judge, Sentinel, Executor, Statute, Praxis, Lexicon, Schema, Instrument, Operator, Reviewer, Auditor, Scout) still goes through it directly, not through `create_child_work` -- only Ledger's and Herald's four sub-agents do, per step 5. Its own module docstring already names this precisely: "Phase 5's SuperOrchestrator becomes the sole caller of TaskService.enqueue; until then this factory is the one place that does." Migrating every one of those ~20 activation call sites onto `create_child_work`-issued durable child tasks is a materially larger undertaking than step 5's "Ledger/Herald" framing -- "every agent activation becomes a durable, budget-checked child task," not four agents -- and is out of this phase's scope, tracked as residual risk. All five delegation boundary tests the plan names for `test_architecture_boundaries.py` are written and pass against real code: `test_manager_holds_no_workflow_authority`, `test_only_the_artifact_service_writes_the_publication_pointer`, `test_concurrent_child_creation_cannot_exceed_parent_ancestor_or_run_budgets`, `test_every_entry_path_submits_a_command`, and `test_no_module_outside_the_super_orchestrator_calls_task_service_enqueue` -- the last two each assert their one documented exception explicitly (`session_intake`/`corpus_study_generate`'s no-provider-work scope; `ActivationFactory.activate`'s interim status) rather than a fictional clean state.
